# Signals API Documentation

## Overview

The Signals API provides HTTP endpoints for querying trading signals generated by the FKS Data Service. Signals are generated in real-time by the `SignalActor`, which monitors technical indicators and detects patterns such as EMA crossovers, RSI zones, MACD crossovers, and confluence conditions.

## Architecture

### Signal Generation Flow

```
WebSocket (Binance) → Router → IndicatorActor → SignalActor → QuestDB
                                      ↓              ↓
                                 (broadcasts)   (broadcasts)
                                      ↓              ↓
                                   Metrics      API Consumers
```

1. **Market Data Ingestion**: Raw candle data flows from exchange WebSockets through the Router
2. **Indicator Calculation**: IndicatorActor processes candles and calculates technical indicators (EMA, RSI, MACD, ATR)
3. **Signal Detection**: SignalActor subscribes to indicator updates and detects trading signals
4. **Persistence**: Signals are stored in QuestDB `signals_crypto` table via ILP (Influx Line Protocol)
5. **Broadcasting**: Signals are broadcast to subscribers in real-time
6. **Metrics**: Prometheus metrics track signal generation rates and types

### Signal Types

| Signal Type | Description | Direction | Conditions |
|------------|-------------|-----------|------------|
| `ema_golden_cross` | EMA-8 crosses above EMA-21 | Bullish | EMA-8 > EMA-21 (previously <=) |
| `ema_death_cross` | EMA-8 crosses below EMA-21 | Bearish | EMA-8 < EMA-21 (previously >=) |
| `rsi_overbought` | RSI enters overbought zone | Bearish | RSI > 70 (previously <=) |
| `rsi_oversold` | RSI enters oversold zone | Bullish | RSI < 30 (previously >=) |
| `rsi_exit_overbought` | RSI exits overbought zone downward | Bearish | RSI < 70 (previously >=) |
| `rsi_exit_oversold` | RSI exits oversold zone upward | Bullish | RSI > 30 (previously <=) |
| `macd_bullish_cross` | MACD crosses above signal line | Bullish | MACD > Signal (previously <=) |
| `macd_bearish_cross` | MACD crosses below signal line | Bearish | MACD < Signal (previously >=) |
| `bullish_confluence` | Multiple bullish signals align | Bullish | EMA golden cross + RSI oversold |
| `bearish_confluence` | Multiple bearish signals align | Bearish | EMA death cross + RSI overbought |

## API Endpoints

### Base URL

```
http://localhost:8080/api/v1
```

### 1. List All Signals

**Endpoint**: `GET /api/v1/signals`

Retrieve all recent signals with optional filtering.

#### Query Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `limit` | integer | No | 100 | Maximum number of signals to return |
| `signal_type` | string | No | - | Filter by signal type (e.g., "ema_golden_cross") |
| `start_time` | string | No | - | Start timestamp (ISO 8601 or Unix ms) |
| `end_time` | string | No | - | End timestamp (ISO 8601 or Unix ms) |
| `min_price` | float | No | - | Minimum price filter |
| `max_price` | float | No | - | Maximum price filter |

#### Example Request

```bash
curl "http://localhost:8080/api/v1/signals?limit=50&signal_type=ema_golden_cross"
```

#### Example Response

```json
{
  "signals": [
    {
      "symbol": "BTCUSD",
      "timeframe": "1m",
      "signal_type": "ema_golden_cross",
      "direction": "bullish",

      "price": 42350.50,
      "ema_8": 42300.25,
      "ema_21": 42280.75,
      "rsi": 55.3,
      "macd": 12.5,

      "metadata": "{\"ema_8_prev\":42280.00,\"ema_21_prev\":42285.00}"
    }

  "limit": 50
}
```

### 2. List Signals by Symbol

**Endpoint**: `GET /api/v1/signals/{symbol}`

Retrieve signals for a specific symbol.

#### Path Parameters

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `symbol` | string | Yes | Trading pair symbol (e.g., "BTCUSD") |

#### Example Request

```bash
curl "http://localhost:8080/api/v1/signals/BTCUSD?limit=100"
```

### 3. List Signals by Symbol and Timeframe

**Endpoint**: `GET /api/v1/signals/{symbol}/{timeframe}`

Retrieve signals for a specific symbol and timeframe combination.

#### Path Parameters

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `symbol` | string | Yes | Trading pair symbol (e.g., "BTCUSD") |
| `timeframe` | string | Yes | Candle timeframe (e.g., "1m", "5m", "15m", "1h", "4h") |

#### Example Request

```bash
curl "http://localhost:8080/api/v1/signals/BTCUSD/1m?limit=20&signal_type=bullish_confluence"
```

## Database Schema

Signals are stored in the QuestDB table `signals_crypto`:

| Column | Type | Description |
|--------|------|-------------|
| `symbol` | STRING | Trading pair symbol |
| `timeframe` | STRING | Candle timeframe interval |
| `signal_type` | STRING | Type of signal (see Signal Types table) |
| `direction` | STRING | "bullish" or "bearish" |
| `timestamp` | TIMESTAMP | When the signal was generated |
| `price` | DOUBLE | Asset price at signal generation |
| `ema_8` | DOUBLE | EMA-8 value at signal time |
| `ema_21` | DOUBLE | EMA-21 value at signal time |
| `rsi` | DOUBLE | RSI value at signal time |
| `macd` | DOUBLE | MACD line value |
| `macd_signal` | DOUBLE | MACD signal line value |
| `metadata` | STRING | JSON metadata (previous values, context) |

### Example Query

```sql
SELECT * FROM signals_crypto
WHERE symbol = 'BTCUSD'
  AND timestamp >= '2025-01-20T00:00:00.000000Z'
  AND signal_type = 'bullish_confluence'
ORDER BY timestamp DESC
LIMIT 100;
```

The SignalActor is configured in `fks/src/data/src/actors/signal.rs`:

```rust

    // EMA Configuration
    pub ema_fast: usize,           // Default: 8
    pub ema_slow: usize,           // Default: 21
    
    // RSI Configuration
    pub rsi_overbought: f64,       // Default: 70.0
    pub rsi_oversold: f64,         // Default: 30.0
    
    // MACD Configuration
    pub macd_fast: usize,          // Default: 12
    pub macd_slow: usize,          // Default: 26
    pub macd_signal: usize,        // Default: 9
}
```

| Variable | Default | Description |

| `QUESTDB_HTTP_PORT` | `9000` | QuestDB HTTP API port |
| `QUESTDB_ILP_PORT` | `9009` | QuestDB ILP (write) port |

## Prometheus Metrics

The SignalActor exposes the following Prometheus metrics:

| Metric | Type | Labels | Description |
|--------|------|--------|-------------|
| `signals_generated_total` | Counter | `symbol`, `timeframe`, `signal_type`, `direction` | Total signals generated |
| `signal_generation_errors_total` | Counter | `error_type` | Total signal generation errors |
| `signal_processing_duration_seconds` | Histogram | `signal_type` | Time to process and generate signals |

### Example Prometheus Queries

```promql
# Signal generation rate (per minute)
rate(signals_generated_total[1m])

# Signals by type
sum by (signal_type) (signals_generated_total)

# Bullish vs Bearish signals
sum by (direction) (signals_generated_total)

# Signal generation for specific symbol
sum by (signal_type) (signals_generated_total{symbol="BTCUSD"})
```

## Grafana Alerts

Alert rules are defined in `fks/config/prometheus/alerts/technical-indicators.yml`:

### Signal Generation Halted

Fires when no signals have been generated in the last 5 minutes.

```yaml
- alert: SignalGenerationHalted
  expr: rate(signals_generated_total[5m]) == 0
  for: 5m
  severity: warning
```

### High-Confidence Signals

Alerts for confluence signals (multiple indicators aligned):

```yaml
- alert: BullishConfluence
  expr: rate(signals_generated_total{signal_type="bullish_confluence"}[1m]) > 0
  severity: info

- alert: BearishConfluence
  expr: rate(signals_generated_total{signal_type="bearish_confluence"}[1m]) > 0
  severity: info
```

## Integration Guide

### Starting the Signal Actor

The SignalActor is automatically started when the data-service binary launches:

```bash
# Via Docker Compose
docker-compose up -d data-service

# Via Cargo
cd src/data
cargo run --release
```

Startup logs:

```
🎯 Starting signal actor...
✅ Signal actor started (EMA cross, RSI zones, MACD cross, confluence)
```

### Subscribing to Real-Time Signals

The SignalActor broadcasts signals via a Tokio broadcast channel. To subscribe:

```rust
use crate::actors::signal::{Signal, SignalActor};

// Get reference to SignalActor from AppState
let signal_actor: Arc<SignalActor> = /* ... */;

// Subscribe to signal broadcast
let mut signal_rx = signal_actor.signal_tx.subscribe();

// Listen for signals
tokio::spawn(async move {
    while let Ok(signal) = signal_rx.recv().await {
        println!("Received signal: {:?}", signal);
        // Process signal (e.g., trigger trade, send notification)
    }
});
```

### Querying Historical Signals

Use the HTTP API to fetch historical signals:

```python
import requests

# Fetch recent golden cross signals
response = requests.get(
    "http://localhost:8080/api/v1/signals/BTCUSD/1m",
    params={
        "signal_type": "ema_golden_cross",
        "limit": 50,
        "start_time": "2025-01-20T00:00:00Z"
    }
)

signals = response.json()["signals"]
for signal in signals:
    print(f"{signal['timestamp']}: {signal['signal_type']} @ {signal['price']}")
```

### Building Trading Strategies

Signals can be used to build automated trading strategies:

```python
# Example: Simple EMA crossover strategy
def on_signal(signal):
    if signal["signal_type"] == "ema_golden_cross":
        # Open long position
        place_order(
            symbol=signal["symbol"],
            side="BUY",
            price=signal["price"]
        )
    elif signal["signal_type"] == "ema_death_cross":
        # Close long / open short
        place_order(
            symbol=signal["symbol"],
            side="SELL",
            price=signal["price"]
        )
```

## Troubleshooting

### No Signals Generated

**Symptom**: `/api/v1/signals/stats` shows 0 total signals

**Possible Causes**:
1. Indicators not warmed up yet (need 50+ candles for EMA-21, 200+ for full history)
2. SignalActor not started
3. WebSocket connection issues (no new candle data)

**Resolution**:
```bash
# Check indicator warmup status
curl http://localhost:8080/api/v1/indicators/BTCUSD/1m/status

# Force deep warmup
curl -X POST http://localhost:8080/api/v1/indicators/warmup/deep

# Check logs
docker-compose logs -f data-service | grep -i signal
```

### Signals Not Persisting

**Symptom**: Signals appear in logs but not in QuestDB

**Possible Causes**:
1. QuestDB connection issues
2. ILP writer buffer not flushing
3. Table schema mismatch

**Resolution**:
```bash
# Check QuestDB connectivity
curl http://localhost:9000/exec?query=SELECT+*+FROM+signals_crypto+LIMIT+1

# Check ILP writer metrics
curl http://localhost:8080/metrics | grep ilp_

# Verify table exists
docker exec -it questdb psql -c "SHOW TABLES;"
```

### High Signal Volume

**Symptom**: Too many signals generated, overwhelming downstream systems

**Possible Causes**:
1. Low timeframe (1m) generates more signals than higher timeframes
2. Volatile market conditions
3. Signal thresholds too sensitive

**Resolution**:
- Increase timeframe to 5m, 15m, or 1h
- Adjust RSI thresholds (e.g., 75/25 instead of 70/30)
- Filter for confluence signals only
- Add volume or volatility filters

## Best Practices

1. **Use Confluence Signals**: These have higher accuracy than single-indicator signals
2. **Multi-Timeframe Analysis**: Confirm 1m signals with 5m or 15m signals
3. **Backtest Before Live Trading**: Use historical signal data to validate strategies
4. **Set Alert Thresholds**: Don't act on every signal; use Prometheus alerts for high-confidence patterns
5. **Monitor Signal Quality**: Track win/loss ratios and adjust thresholds accordingly
6. **Rate Limit Actions**: Don't execute trades on every signal; implement cooldown periods
